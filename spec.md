# Budget App — Build Plan

A private, local-only desktop budgeting app for Windows, organized around **pay periods** (one view per paycheck, like a spreadsheet tab per paycheck), with optional access from an iPhone over the home network or Tailscale.

This plan is written for Claude Code. Build it **one phase at a time**, in order (§10). Finish each phase's acceptance criteria and tests before starting the next. If anything here is ambiguous or seems wrong once you're in the code, **stop and ask** rather than guessing.

Mockups for every screen are in `design/` (see §9). They show layout, hierarchy and behavior. **All numbers in them are sample data — never hard-code them.**

---

## 1. Ground rules (apply to every phase)

### Privacy — non-negotiable
- **All data stays on the user's computer.** No cloud services, no third-party APIs, no bank connections, no sync services.
- **No telemetry, analytics, crash reporting, or update checks.** Do not add any dependency that phones home.
- **No runtime internet requests.** Fonts, icons, chart libraries and all assets are bundled locally (no Google Fonts or CDN links, even though the mockups use them for preview).
- PDF reading (pay stubs, receipts) and any text recognition (OCR) run **on the PC**.
- The only network listener is the app's own local HTTP server (§3). It binds to `127.0.0.1` by default. Phone access is **off by default**.
- Strict Content Security Policy in Tauri that blocks external origins.

### Money, rates and dates
- **Store money as integer cents** (`INTEGER` in SQLite, `long` in Java, number of cents in TypeScript). $14.99 is stored as `1499`. Convert to dollars only for display. Wrap it in a small `Money` value type rather than passing raw longs around.
- **Store rates as basis points** (4.10% = `410`). Interest, growth and amortization use `BigDecimal` internally and round to cents with one documented rule (`RoundingMode.HALF_EVEN`) before storing or displaying. Never use `double` for money.
- Dates are local calendar dates stored as `YYYY-MM-DD` text.

### Every amount is the user's to change
- Any amount the app calculates or estimates (bill estimates, interest, growth, card estimates, suggestions, projected balances) can be typed over. The typed value simply **becomes the value**.
- There is **no "revert to calculated" button**. The original projected value is kept in the database and shown on hover (desktop) / long-press (phone), and in the Projected vs. Actual report.
- **Estimated amounts** are shown inside a **light blue box** (not an "est." tag). Final amounts use the same box size with no fill, so amount columns stay aligned. A small key ("$0.00 = estimate") appears where estimates are shown. An amount stops being an estimate when the user edits it, marks it paid, or unchecks "Estimate, not final yet".

### Pickers, not free text
- Anything chosen from a list (category, tag, account, bucket, payee, frequency, month, day, settings options) uses a **dropdown**, never a free-text field.
- Lists the user builds (categories, tags, payees, accounts) use a **type-to-filter picker**: typing filters existing entries; if nothing matches, the last option is **Add "…" as new**. This prevents misspellings. See `design/picker.png`.

### Colors are the user's choice
- **Categories, tags, accounts and buckets** each have a color the user picks. Clicking any color dot opens a **color picker**: a row of preset swatches, the user's recently used colors first, and a custom option that accepts any hex code.
- The app's **accent color** (buttons, highlights, current pay period) is a setting under Appearance, using the same picker.
- The mockup colors are only defaults for new installs.
- **Readability**: text drawn on a user color automatically switches between dark and light to keep at least 4.5:1 contrast. The user's color is never changed.
- Charts, pills, bucket bars and dots all read colors from the data, never from hard-coded values.

### Code quality
- Calculation logic (pay periods, recurrence, period assignment, balances, interest, growth, amortization, suggestions, planner) lives in a **separate Java module (`engine`) with no database, HTTP or UI dependencies**, covered by JUnit tests. Write the tests from §5 **before** wiring up the UI.
- Use Java records for data, `java.time.LocalDate` for dates, and constructor injection without a DI framework. Keep it plain and readable.
- Commit at the end of each phase with a clear message.

The frontend talks to the backend **only through the HTTP API** (no Tauri `invoke` commands), so the desktop window and the phone's browser run the same React app against the same API.

### The installer (what the end user experiences)
- **One `.exe` installer** (Tauri's NSIS bundle). Double-click, Next, Finish. Nothing else to install or configure.
- Installs **per user, no admin rights needed**, into the user's app folder, with Start menu and optional desktop shortcuts.
- Bundles everything: the trimmed Java runtime, the backend, the React build, fonts and icons. **No separate Java, Node or database install.**
- **WebView2** (Windows' built-in browser engine, already on Windows 10/11): use Tauri's embedded bootstrapper so it's installed automatically if missing.
- First launch creates the app data folder and database, runs migrations, and opens the setup wizard.
- Upgrades: running a newer installer over an existing install keeps all data; migrations run on next launch. A database backup is taken automatically before migrations run.
- Uninstall removes the program but **keeps the data folder** unless the user ticks "also delete my data".
- No auto-update (no network). Updating means running a newer installer.

### Development environment
- **Builds of the installer happen on Windows** (Tauri and jpackage produce Windows output only when run on Windows). Install once: JDK 21, Maven, Node LTS, Rust toolchain (only so Tauri can compile its small wrapper), and the Visual Studio C++ Build Tools that Tauri requires.
- **No Docker.** Day-to-day work runs straight on Windows: the backend jar from the Maven wrapper and the Vite dev server (`npm run dev`, which forwards `/api` to the backend), so most development happens in the browser without Tauri. See `README.md`.
- One script (`build-installer.ps1`) runs on Windows and produces the installer: tests → backend jar → jlink/jpackage app image → frontend build → Tauri bundle. Before bundling it starts the packaged backend once on a throwaway data folder and requires it to serve the UI, because the tests run on the full JDK and cannot notice a module missing from the trimmed runtime.

## 3. Architecture

```
┌──────────────── Windows PC ──────────────────────┐
│  Tauri app (window only)                         │
│  ┌──────────────┐  HTTP (127.0.0.1:port)         │
│  │ WebView      │ ─────────────┐                 │
│  │ (React app)  │              ▼                 │
│  └──────────────┘   ┌──────────────────────┐     │
│        starts/stops │ Java backend process │     │
│        ───────────► │ Javalin + engine     │     │
│                     │ SQLite + Flyway      │     │
│                     │ files/ (receipts…)   │     │
│                     └──────────┬───────────┘     │
└────────────────────────────────┼─────────────────┘
                                 ▼ (only when enabled)
                  iPhone Safari over home Wi-Fi or Tailscale
```

### Backend lifecycle (solve this in Phase 0 — it's the riskiest part)
1. Tauri starts the bundled backend launcher (from the jpackage app image in Tauri's resources), passing its own process ID and the app data folder.
2. The backend runs Flyway migrations, binds Javalin to `127.0.0.1` on the configured port (default 4873; if busy, the next free port), then prints one line to stdout: `READY port=NNNN`.
3. Tauri waits for that line (with a timeout and a friendly error screen if it never comes), then points the window at `http://127.0.0.1:NNNN/`. The backend serves the React build itself, so there is one origin and no CORS. Since Phase 10 the window is on screen from the start, on a page bundled with the shell that says "Opening your budget…", so the wait is not a blank.
4. On window close, Tauri asks the backend to shut down (`POST /api/shutdown`, local only), then kills the process if it hasn't exited after a few seconds.
5. The backend also watches Tauri's process ID (`ProcessHandle.of(pid).onExit()`) and exits by itself if Tauri dies, so no stray server is ever left running.
6. Only one backend may run at a time (lock file in the app data folder).
- Attachments (receipts, invoices, pay stubs) are copied into `%APPDATA%\<AppName>\files\`, named by content hash, and referenced from the database. Originals are never modified.
- **Phone access (Phase 12):** when enabled, the server also listens on the chosen interface (LAN IP or Tailscale IP). Plain HTTP on home Wi-Fi is unencrypted, so Settings shows a warning and recommends Tailscale. The PIN is always required. The phone shows "Can't reach your PC" when the app isn't running.

## 4. Data model

Names are suggestions; keep the concepts. Money = integer cents, rates = basis points.

### 4.1 App and security
- **settings** — key/value: theme (`light` | `dark` | `system`), density, accent color, projection horizon (default 12 months), budget year start (month + day, default Jan 1), plan-next-year reminder date (default Oct 1), auto-lock minutes, promo warning days (default 60), unpaid-bill highlight days (default 3), start with amounts hidden, backup folder and count, phone access settings, primary income source.
- **auth** — `pin_hash`, `recovery_code_hash`, failed attempts, lockout-until. As built (Phase 6, migration `V19`): one row, plus `offer_dismissed` (the first-launch offer of a PIN was answered). It is left out of the change log, so Undo never brings a PIN back and no hash is copied there.
- As built (Phase 6), the settings with a control are `theme`, `accent_color`, `projection_horizon_months`, `promo_warning_days`, `unpaid_highlight_days` (0, 1, 2, 3, 5, 7, 10 or 14; default 3), `auto_lock_minutes` (1, 5, 15, 30 or 60; default 15), `start_amounts_hidden`, `backup_keep_count` (7, 14, 30, 60 or 90; default 30), `backup_folder` (set only through the folder browser) and, since Phase 8, `default_date` (empty for today, or a day that is today or earlier in a supported year: the date new things start on, §6). Which income source is primary is kept on the source, not as a setting. Budget year start, the plan reminder, phone access and density have no setting yet (§12).
- **change_log** — before/after of every edit, powering Undo. As built: `change_groups` holds one row per request that changed something and `change_log` one row per table row it added, altered or removed (`table_name, op, before, after`, the rows as JSON). The rows are written by database triggers that the server rebuilds from the live schema every time it opens the database, so every table and column is covered without each feature having to remember; `change_recording` says which change, if any, is being recorded. The newest 100 changes are kept. Undo puts back the newest change and forgets it (there is no redo). Erasing all data is not recorded.

### 4.2 Accounts, buckets, assets
- **accounts** — `id, name, institution, type, subtype_label, color, low_balance_threshold (nullable), sort_order, archived`.
  - `type`: `checking` | `savings` | `credit_card` | `investment` | `loan`. `subtype_label` is free text chosen by the user (e.g. "401(k)", "Brokerage", "HSA", "Mortgage").
- **balance_entries** — `account_id, date, amount, note`. A user-entered **actual** balance. Projections roll forward from the latest entry on or before a date. (Not reconciliation — just "the real number is X".) The balance stands for the **start** of its day: whatever is dated that day or later is still to come (§5.3).
- **rate_history** — `account_id, kind (apy | growth | apr | loan_rate), rate_bp, effective_date`. A change applies from its date forward.
- **buckets** — `id, account_id, name, color, goal_amount (nullable), goal_date (nullable), note, sort_order, archived, opened_on`. With a goal and a goal date, the bucket reports what it is projected to hold on that date from what is already scheduled, how far short that is, and what closing the gap takes per paycheck (shortfall ÷ paydays left, rounded up to the cent) or per month; one click adds that as an every-paycheck bucket move ending on the goal date. **Checking and savings only.** Buckets don't change the account balance; they reduce **available**. Schedules, save-ups and interest reach a bucket only from `opened_on`, shown as **Counts from**: a new bucket is never back-filled from older dates unless the user says so. It defaults to the current pay period's payday, so the paycheck in hand is included, and can be set to any day up to today. An archived bucket holds nothing.
- **bucket_changes** — `bucket_id, date, amount (+/−), source (manual | transfer | bucket_move | interest | income_split), note`. As built, only what the user moves by hand is stored (`manual`); recurring bucket moves, transfers into a bucket, splits, save-ups and interest shares are worked out on every request, like occurrences, so they always follow the current schedules.
- **interest_settings** — `account_id, credit_day (1–31; 31 means the last day), destination (unassigned | bucket | proportional), destination_bucket_id`. No row means the defaults: last day, unassigned.
- **assets** — `id, name, kind (home | vehicle | other), color, appreciation_bp (nullable), linked_loan_account_id, sort_order, archived, created_at`. As built (migration `V12`): the rate is zero or more; something that loses value gets a new, lower value entered instead (decided with Rachel, 2026-10-09). **Changed 2026-10-11** (Rachel: "something like a car depreciates over time"): an asset can also lose value by a yearly rate, up to 99%. Migration `V20` keeps the loss in its own column, `depreciation_bp`, because the check on `appreciation_bp` cannot be changed without rebuilding a table others refer to; at most one of the two is set. In the API it is one signed figure, `appreciationBp`, below zero for a loss. The linked account must be a loan; deleting that loan leaves the asset owned outright.
- **asset_values** — `asset_id, date, value`. One per asset per day; the same day again replaces it.

### 4.3 Income and pay stubs
- **income_sources** — `id, name, deposit_account_id, gross_amount (nullable), net_amount, net_is_estimate, schedule_rule_id, is_primary`. Multiple sources allowed; the **primary** source's schedule defines pay periods. The first source is always primary, and there is exactly one while any source exists.
- **income_pay_changes** — `id, income_source_id, effective_date, gross_amount, net_amount, net_is_estimate, match_to_account_id, match_mode, match_fixed_amount, match_bp, match_cap_bp_of_gross, match_within_cap` (migration `V14`). A change of pay from a date on: a raise, new deductions, a different match. The source's own row keeps the amounts it started with; each row here takes over from its `effective_date`, one per source per day. Its deductions are `paycheck_deductions` rows carrying its `pay_change_id` (NULL = the amounts the source started with), and its match sits on the row itself, mirroring `employer_match`. A paycheck uses the latest change dated on or before the day its schedule names. The name, deposit account, schedule and primary flag are not dated: they belong to the source as a whole.
- **paycheck_overrides** — `income_source_id, scheduled_date, net_amount, projected_amount`. One paycheck's amount typed over ("just this one"), keyed by the date the schedule names (which stays put when a holiday moves the payday). `projected_amount` keeps what was shown before the first edit.
- **paycheck_deductions** — `income_source_id, name, amount, to_account_id, percent_bp (nullable)` (401(k), HSA…). These never pass through checking. A deduction is a dollar amount or, with `percent_bp` (migration `V13`), a share of gross pay; `amount` then holds what that comes to, worked out from the gross amount each time the source is saved. A share needs the gross amount.
- **employer_match** — `income_source_id, to_account_id, mode (fixed | formula), fixed_amount, match_bp, cap_bp_of_gross`. As built (migration `V12`): one per income source, a single tier (decided with Rachel, 2026-10-09), paid into an investment account only. `formula` checks the contribution against the source's gross amount; with no gross amount it stands only with `contribution_within_cap` (migration `V13`), the user's confirmation that what they put in is within the matched share.
- **pay_stubs** — `id, income_source_id, pay_date, file_id, status (review | saved)`.
- **pay_stub_lines** — `pay_stub_id, section (earnings | pre_tax | tax | net | employer), label, amount, ytd_amount, maps_to (gross | contribution | benefit | tax | net | match), maps_to_account_id, confidence`.
- **stub_layouts** — per employer: remembered positions/labels of each line so later stubs fill automatically.
- As built (Phase 8, migration `V22`):
  - `pay_stubs` is `id, income_source_id, file_id, name, pay_date (nullable while in review), status (review | saved), applied (correct | pay_change | paycheck | none; set exactly when saved), created_at`. A stub names its file in `files` directly and carries the file's name itself, so `attachments` (§4.8) was left as it is.
  - `pay_stub_lines` is `id, pay_stub_id, position, section (earnings | pre_tax | tax | after_tax | net | employer), label, amount, ytd_amount, maps_to (gross | contribution | benefit | tax | net | match | ignore), maps_to_account_id, sure`. `after_tax` is its own part of a stub (Roth, parking, garnishments); `ignore` is an employer-paid line that is not followed. `sure` (0 or 1) took the place of `confidence`: a line is either one the reader had to guess at, pointed out until someone has looked at it, or it is not. What is taken out is stored as a positive amount; only earnings can be negative.
  - `stub_layouts` is `id, income_source_id, label_key, section, maps_to, maps_to_account_id`, one row per source per line label (the label lower-cased with its punctuation and spacing evened out). How a line was filed is remembered by its **label**, not its position on the page: payroll companies add and drop rows from one stub to the next, and the label is what stays. It is written when a stub is saved, so a line corrected in review is filed the same way on the next stub.
  - A stub in review changes nothing. Saving asks what it should change (decided 2026-10-12, asked every time): **correct** the amounts in force on its pay date, record a **pay change** from the paycheck it is for (`income_pay_changes`), set **just that paycheck** (`paycheck_overrides`; needs a paycheck within 4 days of the pay date), or **nothing**. Gross is the earnings lines, take-home the net line, and the lines before and after tax become the source's deductions (a contribution keeps its account); taxes stay on the stub; a match line becomes a fixed match unless the source has a formula. A saved stub is opened again with **Edit stub** (`POST /api/pay-stubs/{id}/reopen`), which puts it back in review with every line as it was; what it changed stays until it is saved again, and the save dialog starts on the choice made last time. (First built read-only; Rachel, 2026-10-12: a line filed wrongly is noticed after saving.) Removing a stub leaves what it changed; Undo brings the stub back. A retirement contribution nothing else places (no same-named deduction, not filed before) goes to the account the employer's match goes to.

### 4.4 Schedules
- **schedule_rules** — `id, frequency, interval, day_1, day_2, month, start_date, end_date, weekend_rule`.
  - `frequency`: `every_pay_period` | `weekly` | `biweekly` | `semi_monthly` | `monthly` | `every_n_months` | `yearly` | `one_time` | `manual_dates`.
  - `monthly` accepts a day or `last`; days that don't exist in a month fall to its last day.
  - `weekend_rule`: `none` | `previous_business_day` | `next_business_day`.
- **manual_dates**, **holidays**. US bank holidays are worked out locally (no download) and added a year at a time; each can be switched off, changed or removed, and the user can add their own. `holiday_years_seeded` records which years were added, so a removed holiday never comes back.

### 4.5 Categories and tags
- **categories** — `id, name, color, parent_id (nullable), sort_order`. One per item. Includes income categories (e.g. Income › Bonus).
- **tags** — `id, name, color`. Many per item, via **item_tags** / **entry_tags** link tables.

### 4.6 Recurring items
- **items** — `id, name, kind, amount, amount_mode (per_occurrence | annual), is_estimate, category_id, pay_from_account_id, pay_to_account_id, bucket_id, autopay, placement, schedule_rule_id, save_up_bucket_id (nullable), note, archived`.
  - `kind`: `bill` | `transfer` | `budget` | `bucket_move` | `card_payment`.
  - `pay_from_account_id` can be **any** account, including a credit card (the charge then lands on the card).
  - `bucket_move` moves money from available into a bucket inside the same account (e.g. $50 every paycheck to Holiday gifts).
  - `amount_mode = annual`: the user enters a yearly total. With `save_up_bucket_id` set, the app creates a matching per-paycheck bucket move so the money is there by the due date. As built: any bill or budget can be saved up for, not only yearly totals; each occurrence is shared evenly over the paydays since the one before it (or since saving began), odd cents on the earliest, and leaves the bucket on the day the bill counts. Saving set up part-way through a pay period starts with that period's payday. A skipped occurrence is not saved for.
  - `bucket_id` and `save_up_bucket_id` live on the item's versions, like its other terms, so a change applies from a date on. A transfer can name a bucket in the account it pays into.
  - `placement`: `due_period` | `one_early` (§5.2).
  - `days_after_payday` (0–60, default 0): for an `every_pay_period` schedule, how many days into each period the item is dated. This is how **each budget carries its own date**.
- **item_versions** — "this and all future" edits start a new version effective from a date. As built, `items` holds only what never changes (name, kind, note, archived) and every other column above lives on the version, each with its own `schedule_rule_id`; the earliest version also covers every date before it.
- **occurrence_overrides** — `item_id, original_due_date, amount, due_date, period_override, paid, paid_date, confirmation_code, note, skipped, projected_amount`. "Just this one" edits live here. Occurrences are computed on the fly; only changes are stored.

### 4.7 One-off entries (money in and out)
- **entries** — `id, kind (money_out | money_in | transfer), date, amount, is_estimate, description, payee, category_id, account_id, to_account_id (transfers), note, reimburses_entry_id (nullable)`.
  - Used for one-off expenses (vet emergency, gift, donation), one-off income (bonus, refund, gift, side cash), and one-off transfers.
  - **entry_bucket_splits** — `entry_id, bucket_id, amount` (e.g. put $500 of a bonus into a bucket).
  - **Reimbursement** — `reimbursement_status (none | to_submit | submitted | reimbursed)` on money-out entries; a money-in entry can link to the expense it pays back.
  - As built (Phase 7, migration `V21`): a money-out entry also has `reimbursement_submitted_on` and `reimbursement_to` (who pays it back). Several money-in entries can name the same expense in `reimburses_entry_id`, so it can be paid back in parts; what is still owed is the expense less those, never below zero. A payback that covers the expense marks it reimbursed, and one that arrives while it is still "to submit" marks it submitted. Deleting an expense, or changing it to something that is not money out, lets its paybacks go (they stay as ordinary money in).
- **card_charges** are entries whose account is a credit card.

### 4.8 Attachments
- **files** — `id, hash, original_name, mime, size, created_at`.
- **attachments** — `file_id, owner_type (entry | occurrence | pay_stub | statement), owner_id`.
- As built (Phase 7, migration `V21`):
  - `files` is `id, hash (unique), mime, size, pages (PDFs only), created_at`: one row per distinct file, stored once under `files/<first two of the hash>/<SHA-256>` however many things it is attached to.
  - `attachments` is `id, file_id, name, entry_id | (item_id, scheduled_date) | statement_id, created_at`, with a check that exactly one owner is set. The name is on the attachment, not the file, because the same file can be added twice under different names. Real columns in place of `owner_type, owner_id` let the database remove an attachment with its owner. A pay stub is not an owner here: it names its file itself (`pay_stubs.file_id`, §4.3), and a file is kept while any attachment, pay stub or undoable change names it.
  - Accepted: PDF, JPEG and PNG, told apart by their content and never by the name; up to 25 MB each (`BUDGET_MAX_UPLOAD_MB`) and 20 per thing. A file is never changed. WebP was dropped (the PDF export cannot embed it); iPhone HEIC photos wait for phone access (Phase 12).
  - Removing an attachment only unlinks it, so Undo can put it back. The file itself is deleted at the next start once no attachment and no change that could still be undone names it.

### 4.9 Credit cards and loans
- **card_settings** — `account_id, statement_close_day, due_day, payment_mode (full_balance | statement_balance | minimum | fixed), fixed_payment_amount, autopay, pay_from_account_id`.
- **card_statements** — `account_id, close_date, statement_balance, minimum_due, due_date`.
- **card_promos** — `account_id, label, kind (balance_transfer | purchase | other), rate_bp, start_date, end_date, original_balance, rate_after_bp (nullable → regular APR), deferred_interest`. Several per card allowed.
- **loan_settings** — `account_id, original_principal, rate_bp, term_months, start_date, payment_amount, escrow_insurance, escrow_taxes`.
- As built (Phase 5, migration `V15`):
  - `card_settings` also has `payment_item_id` (the recurring item that is the card's own payment) and `monthly_estimate` (for a card whose charges are not entered one by one). The payment columns (`payment_mode`, `fixed_payment_amount`, `autopay`, `pay_from_account_id`) are a copy of that item, written whenever the item is saved, so the card's projection can read them; they are not set on the card. `pay_from_account_id` is empty while the card has no recurring payment.
  - `card_statements` is unique per card and closing date: the same date again replaces it.
  - `card_promos` also has `payoff_item_id`, the recurring payment the payoff helper added.
  - `loan_settings` has no `rate_bp`: a loan's rate, like a card's APR, is a dated rate in `rate_history` (kinds `loan_rate` and `apr`), so a change of rate never rewrites earlier months. It has `payment_day` (1–31, 31 = last day), and `original_principal`, `term_months` and `start_date` are optional.
  - `loan_settings.payment_item_id` (migration `V16`): the recurring item linked as the loan's payment from the loan's page; emptied when that item is deleted. A transfer into the loan needs no link.

### 4.10 Yearly plans
- **plan_years** — `id, year, status (draft | active | closed), basis (last_12 | last_12_trend | prior_year), created_at`.
- **plan_year_amounts** — `plan_year_id, item_id (or income_source_id), suggested_amount, chosen_amount, chosen_by (suggestion | user)`.
- A **draft** plan can be deleted and redone any time **before its start date**. When the budget year starts, the draft becomes active and its amounts become new item versions effective that day. History is never rewritten.
- As built (Phase 10, migration `V23`):
  - `plan_years` also has `starts_on` (unique; the first day of the plan's budget year), `suggested_as_of` (the day its suggestions were last worked out), `setup` (1 for first-time setup) and `activated_on`. There is one draft at a time.
  - **A draft stores only what was typed.** `plan_year_amounts` holds a row per amount typed in (`chosen_by user`) while the plan is a draft; every other amount is its suggestion, worked out when the plan is opened, as of `suggested_as_of`. When a month has ended since then the plan says so and offers "Use the latest months"; nothing moves until that is pressed. On the day the plan takes effect every amount is written down, suggested and chosen, so a closed plan can still be read.
  - An item's amount is its **total for the plan's year**; an income source's is **take-home pay for one paycheck**.
  - **Taking effect** (at start-up and every hour after, between two changes, in one transaction, not recorded for Undo): each item gets a new version from `starts_on` at the plan's amount ÷ its occurrences in the year, a version dated later than that is left as it is, each income source gets a pay change from that day marked as an estimate, and the plan before it is closed. Nothing dated before `starts_on` is touched.
  - **First-time setup** is a draft of the budget year under way with `setup = 1`: its amounts cannot be typed (what is added in its steps *is* the budget), and finishing makes it the active plan at once.
  - Settings `budget_year_start` (`MM-DD`, default `01-01`) and `plan_reminder` (`MM-DD`, default `10-01`); Feb 29 is refused for both.

### 4.11 Reports
- **saved_reports** — `id, name, definition_json` (date range, filters by tag/category/account/payee/kind, group by, chart type).
- As built (Phase 7, migration `V21`): the name is unique whatever its capitals; up to 100 reports. The definition holds `range` (this year, last year, last 12 months, last 90 days, or custom with `from` and `to` up to ten years apart), `include` (one-off spending, bills, budgets), `groupBy` (month, year, category, tag, payee, account), `show` (chart and table, or table), and the filters `tagIds`, `categoryIds`, `accountIds`, `payees` and `reimbursement`. Within one filter any choice matches; across filters all must. A relative range is worked out on the day the report is opened, so "This year" saved in 2026 shows 2027 next year.
- **Income reports** (Phase 8, decided 2026-10-12; no migration — the definition is JSON): a report is of spending or of income, one or the other (`kind`: `spending`, the default for every report saved before, or `income`). An income report keeps the same dates and `show`, and has its own `incomeInclude` (paychecks, one-off money in, employer match, interest; at least one), `incomeGroupBy` (month, year, income source, account it landed in, pay period) and the filters `sourceIds` and `accountIds`; tags, categories, payees and reimbursement say nothing in it.
  - **What counts:** every paycheck at what it actually was (pay changes and amounts typed over one paycheck included); one-off money in, except money that pays back an expense — that is the expense coming back; what an employer adds to a retirement account; interest on checking and savings accounts as Budget works it out (always an estimate). Transfers never count.
  - **Figures:** gross pay, taxes, other deductions and take-home, for each group and the whole. A paycheck with a saved pay stub (dated within four days of it) uses the stub's own lines; otherwise the income source's figures in force that day, with taxes taken as gross − deductions − take-home. A paycheck with no gross amount is in the take-home only, and the report says how many there are.
  - **Received** is take-home + one-off money in + interest. The **employer match is beside it, never in it**: it does not reach an account to spend from.
  - Filtering by income source leaves out what has none (one-offs, interest). The sums are the engine's (`engine/reports/IncomeReport`).
- **Projected vs. actual reports** (Phase 9, decided 2026-10-12; no migration): a third `kind`, `projected_vs_actual`. It keeps the dates, and has its own `compareInclude` (bills & expenses, budgets, paychecks; at least one), `compareGroupBy` (month, year, category, item), `changedOnly` ("Only what was typed over") and the filters `tagIds`, `categoryIds` and `accountIds`. It has no chart and no "with receipts" export.
  - **Projected** is what Budget worked out for that date; **actual** is the amount typed over it, or the same figure when nothing was typed (§5.10). For a **budget** that is the whole rule (Rachel, 2026-10-12): an untouched budget line counts as spent as planned.
  - **Spending and paychecks are two sums, never one**: each has its own projected, actual and difference, and its own table. A tag or category filter leaves paychecks out, since they have neither.
  - One-off spending is not in it: nothing was projected for it. The sums are the engine's (`engine/reports/ProjectedVsActual`).

## 5. Calculation engine (`engine` module, pure Java, JUnit-tested)

### 5.1 Pay periods
- Periods come from the **primary** income source. A period runs from one payday up to the day before the next.
- Generated through the projection horizon. Weekend/holiday rules move paydays and therefore boundaries.
- **Tests:** semi-monthly 1st & 15th; semi-monthly 15th & last (Feb leap/non-leap); biweekly across a year boundary; weekly; monthly; manual dates; payday Sunday Nov 1, 2026 with `previous_business_day` → Fri Oct 30; with a user holiday on that Friday → Thu Oct 29.

### 5.2 Which period an item lands in
For an occurrence due on **D**, with **P** = the period containing D:
- It lands in **P − 1** if `placement = one_early`, **or** if D is a payday (first day of P) **and** the item is **not** autopay.
- Otherwise it lands in **P**.
- A user can move a single occurrence to another period (stored as an override).
- **Tests:** rent due Oct 1 (payday), manual → Sep 15–30 period; same rent on autopay → Oct 1–14; electric due Oct 16 `one_early` → Oct 1–14; `due_period` → Oct 15–31; an item that is both `one_early` and due on payday moves back **one** period, not two.

### 5.3 Balance projection (per account)
- Start from the latest `balance_entry` on or before the period start.
- Apply in date order: paychecks (net), one-off money in/out, bills, transfers, card payments, interest, growth, charges.
- **Each budget line has its own date** (decided 2026-10-06; there is no global budget-timing setting): the period's first day by default, changeable for one occurrence (`occurrence_overrides.due_date`) or for this and all future (`days_after_payday`).
- An occurrence always counts on a day **inside the period that pays for it** (its due date, brought inside that period: "due Oct 16, pay by Oct 14"), so a period's figures add up to what it lists.
- **Entered balances and unpaid items.** A balance entered for a day is what the account held at the start of that day. Anything dated earlier is taken as already in it — except an item the user pays by hand that is **not marked paid** and either is not due yet or belongs to the pay period the balance was entered in. Those still come out, on the day of the balance, and the period names them as carried over. Autopay items, paychecks and one-offs are assumed to happen on their date. Older unticked items are taken as paid, so nobody has to tick off months of history.
- For a credit card or loan the balance is what is owed: charges raise it, payments lower it.
- Per period and account: starting balance, total in, total out, projected ending, **lowest point**, **available after buckets**.
- Low-balance flag only if the user set a threshold for that account. A period is flagged when its lowest point (its starting balance included) is under the threshold.

### 5.4 Savings interest
- On the account's credit day: estimated interest = balance × ((1 + APY)^(1/12) − 1), credited to the chosen destination, shown as an estimate.
- A user-entered balance replaces the projection from that date.
- As built: the balance is the one at the start of the credit day; the rate is the one in force that day; an account earns interest once it has an APY in its rate history, from its first entered balance on. Interest counts as money in. `proportional` gives each bucket its share of the account (bucket ÷ the larger of the balance and all buckets, HALF_EVEN); the rest stays unassigned. The estimate cannot be typed over — entering the real balance is how it is corrected. A balance entered **on** a credit day is taken to hold that month's interest already: the estimate is not added on top of it or listed under Income, but a bucket still gets its share, worked out on what the account was projected to hold before that balance. On the day of the very first balance there is nothing earlier to work it out on, so nothing is credited.

### 5.5 Investments
- Contributions: paycheck deductions, employer match, transfers.
- Growth: monthly from the user's assumed rate, always labeled as an assumption.
- **Gain/loss uses only user-entered balances**: ending − starting − net contributions. A projection being off is never a loss.
- **Match formula tests:** gross $3,600, employee $150 (4.17%), match 50% up to 6% → $75. Employee $216 (6%) → $108. Employee $300 → capped at 50% × 6% × $3,600 = $108.
- As built:
  - **Contributions** arrive on payday: each deduction that names an account, and the match, are money into that account (transaction kinds `contribution`, `employer_match`). They never pass through checking and are not part of take-home pay.
  - **Match formula**: the smaller of what the employee puts in and cap × gross, times the match rate, HALF_EVEN. "What the employee puts in" is that source's deductions into the match's own account. The Income screen says when the contribution is under the cap, and how much more each paycheck would earn the whole match.
  - **Percentages or dollars** (Rachel, 2026-10-10: "100% match up to 6%, and then maybe my contribution is a dollar amount or 6% of gross. but also could just be numbers like today"): the match is a percentage rule or a fixed dollar amount, and each contribution is dollars or a percent of gross pay. A contribution as a percent is refused without a gross amount. A percentage match with a dollar contribution and no gross amount cannot be checked against the cap, so the form asks for a tick — "What I put in is within the 6% of my pay that is matched" — or the gross amount; ticked, all of the contribution is matched, and the Income screen says the match rests on that confirmation. Once a gross amount is entered the tick is dropped and the cap is checked.
  - **A raise** (Rachel, 2026-10-10: "It's really the same income source but all the numbers on it change … looks like it goes back through all of time right now with no date defined"): an income source's amounts — take-home, gross, deductions, match — can change from a date on, and paychecks before it keep what they had. Each source's own page has **Record a pay change**, and the Edit form asks **When the amounts below apply**: "I'm correcting the amounts" (the default; replaces the amounts in force today, and says which paychecks that reaches) or "My pay changes from a date" (any day, past or future; the first paycheck on or after it is the first with the new amounts). Once there is a change, the source shows its **Pay history**, newest first, each entry marked "in use now" or "still to come" with its own Edit, and Remove for a dated change (the amounts before it then carry on). Saving a change whose amounts do not differ from that day's records nothing; the same day again replaces that change; a later-dated change is left alone. The source's top-level amounts everywhere are the ones in force today. A paycheck typed over ("just this one") keeps its amount through a raise. A deduction given as a percent of gross is worked out again from the new gross amount.
  - **Growth** builds up a little every day (changed 2026-10-11; it used to arrive in one lump on the last day of the month, which made the pay periods holding a month-end look as if the contribution had doubled). The daily rate is the 365th root of the yearly one, on the balance each day starts with, from the day after the first entered balance. Only whole cents are added and the rest is carried to the next day, so a small balance is not rounded up into growing faster than its rate; a year comes to the yearly rate to within a cent. Nothing is added on the day of an entered balance, which already holds what the account really did. It is listed as "Assumed growth": one line per pay period on the pay period screen, on its own line apart from "Coming in" (which is then only real money), and one line per month in the account's own list. It is never under Income, never a deposit, and it cannot be typed over — entering the real balance replaces it.
  - **Change this year** (every account): from January 1, or from the first balance entered when that is later, to today, split into what was put in and the rest.
  - **Growth per entered balance**: change since the entry before − what was put in between the two. Both figures are worked out from entered balances only.

### 5.6 Credit cards
- Balance rises with charges (actual or estimated), bills paid from the card, one-offs on the card, and estimated interest; falls with payments.
- Payment by mode: full balance, statement balance (user-entered or estimated), minimum, fixed.
  - **Statement balance, estimated** (asked for by Rachel on 2026-10-09): the card's projected balance as of its statement closing date is the estimated payment on the next due date, so a recurring card payment can be set to "pay the statement balance" and follow the card instead of a typed amount.
- Interest estimate when a balance is carried, using the promo rate while active, then `rate_after` / regular APR.
- **Promos:** warn within the user's lead time; stronger warning for deferred interest. **Payoff helper:** remaining promo balance ÷ number of primary paydays before the end date, rounded up to the cent; one-click "add as recurring payment". Test: $2,400 before Mar 15, 2027 with 10 paydays left → $240.00.
- As built (Phase 5):
  - **Statement cycle**: a statement closes on the card's closing day each month and is due on the first due day after it. A statement the user enters stands in for the balance from the day after it closed, and replaces any estimate.
  - **The card's own payment** is a recurring `card_payment` item, and everything about how the card is paid is set on that item's page like any other item (2026-10-10: "payment settings are on the recurring payments page if that's where the payment lives"). Its Amount card has **How much it pays**: a fixed amount, the statement balance, the full balance or the minimum. Unless it is fixed, or one occurrence was typed over, its amount is worked out per statement — it "follows the card". Paid from, autopay and which paycheck pays it are the item's own cards. A card has one such payment: the first card payment added into it (or the one already there when its dates are entered); a second payment into the same card must have a fixed amount. The card's page has no payment setting: it shows the next payment with a link to the item, or "Add it as a recurring payment", which opens the add-item form already pointed at the card. Moving the card's due day moves a monthly payment with it.
  - **Amounts by mode**: full balance = what is owed on the due day; statement balance = the statement entered, or the projected balance at the close; minimum = the minimum entered, or an estimate by the card's own rule, never more than is owed. The rule is a share of the statement balance, with or without that month's interest added, and never less than a floor; it starts as 1% plus interest and at least $25, and is changed on the card's page under **Minimum payment estimate** (`card_settings.minimum_share_bp`, `minimum_floor`, `minimum_plus_interest`, migration `V17`), because card companies differ; fixed = the amount set.
  - **Interest**: a month at APR ÷ 12 on what was left unpaid from the statement before, added at the close. Paying the statement in full means none. A carried balance is shared out lowest rate first, each promotion up to what is left of the balance it started with; once a promotion ends, its share is charged `rate_after`, or the regular APR.
  - **Deferred interest**: if a deferred promotion still has a balance on its end date, interest for the whole promotion on its starting balance is charged that day.
  - **Monthly estimate**: one estimate of spending is added at each close until the real statement is entered (decided 2026-10-10, §11).
  - **Warnings**: from `promo_warning_days` before the end (a setting, 60 by default; choices 30, 45, 60, 90, 120 — its control arrives with Settings in Phase 6), only while a balance is on the promotion; `soon_deferred` is the stronger one, `ended` once it has passed with a balance left. A pay period is flagged when a promotion ends in it with a balance projected to remain.
  - **Payoff helper**: paydays strictly after today and before the end date. The payment it adds runs every pay period from the next payday to the day before the end, from the card's pay-from account, or the primary paycheck's account when none is set.

### 5.7 Loans, home, net worth
- Amortization: each payment splits into interest and principal; escrow is part of the payment but not principal.
- Home value from user entries, with optional appreciation between entries. Equity = value − linked loan balance. A yearly loss works the same way downwards (2026-10-11): by whole months since the latest value entered, `value × (1 − loss)^(months/12)`, so a year at 15% leaves exactly 85%, and it never goes below zero.
- Net worth = cash + savings + investments + assets − card balances − loan balances.
- As built (loans, Phase 5):
  - A month's interest (rate ÷ 12, HALF_EVEN) is added to what is owed on the payment day; it is skipped on a day a balance was entered, which already includes it.
  - A scheduled (recurring) payment into the loan has the month's insurance and taxes taken out before it lowers the loan, at most one month's escrow per calendar month. An extra one-off payment goes wholly to the loan.
  - **What pays a loan** (Rachel, 2026-10-10: "the monthly payment should be linked to a recurring charge… you should be able to enter from the loan screen or recurring items screen"). The payment on the loan's page is a description; the money moves through a recurring item. Three ways in: a recurring **transfer into the loan** (Recurring items); **linking an item that already exists** from the loan's Monthly payment form (a bill, or a transfer into the loan), after which each of its payments lowers the loan as well as leaving its account; or **Add it as a recurring payment** on the loan's page, which creates that transfer from the account chosen.
  - **Before anything is scheduled, the payment is taken as made**: on each payment day up to the month of the first scheduled payment (or always, while nothing is scheduled), the payment less escrow comes off the loan. So a loan entered as it stood on the day it started is paid down to today rather than only gathering interest. These lines show among the loan's transactions as "Monthly payment (taken as made)" and leave no account. The first build left this out: a loan entered at its 2016 balance showed ten years of interest and no payments.
  - The loan's page shows the next payment shared out, the payoff date and the interest still to pay at this payment and rate, year by year, and — when the amount borrowed, term and rate are all known — the level payment those terms work out to. If the payment does not cover a month's interest it says so, and no payoff date is given.
  - What is owed always starts from the balance the user enters; the terms never overwrite it. Equity and net worth use the ledger's balance, so they move with each payment.
- As built (home and net worth):
  - **Asset value on a day**: the latest value entered on or before it, compounded for each whole month since at the monthly rate of its assumed yearly growth. With no rate, it stays as entered. A value worked out this way is marked as an estimate wherever it shows. An asset with no value entered counts for nothing.
  - **Equity**: value − what the linked loan is owed today.
  - **Net worth** is today's figure: every account's balance at the end of today plus every asset, less cards and loans. Archived accounts and assets are left out. A card or loan balance is entered as the amount owed.

### 5.8 Annual costs and suggestions
- **Annual totals** per item and category for calendar years and **rolling 12 months**, plus % change.
  - As built (Phase 9, `engine/reports/AnnualCosts`): three windows side by side — this calendar year and the two before, or the twelve months ending last month and the two twelve-month spans before those. The change is the newest window against the one before it, in basis points, and is left empty ("new") when the earlier one holds nothing. This calendar year counts what is still to come at what is budgeted, and the screen says from which day. Per month is the newest window ÷ 12. Archived items are left out.
  - **By month** for one bill or budget: this year beside last, the highest and lowest month, the average, and **too low** when the average month so far is more than the amount set now.
- **Suggestions for next year**, using the plan's basis:
  - `last_12`: total of the last 12 full months.
  - `last_12_trend`: last 12 months × (1 + year-over-year % change), rounded to the dollar.
  - `prior_year`: the most recent full calendar year.
- Because planning normally happens in **October**, the default basis is `last_12_trend` and the window is the 12 months ending last month (e.g. Oct 2025 – Sep 2026).
- Fixed-amount items (loan payments) are suggested unchanged.
- Annual items with a save-up show the per-paycheck amount (annual ÷ paydays before the due date).
- As built (Phase 10, `engine/plans/PlanSuggestions`):
  - The trend is the 12 months against the 12 before; with nothing in the earlier span there is no trend and `last_12_trend` suggests the plain 12 months. A suggestion is never below zero.
  - **Under 12 months of history** (decided with Rachel, 2026-10-12): the amount set now over a year, marked "not enough history yet", with no trend, whatever the basis.
  - **Suggested unchanged:** a transfer into a loan (listed with Bills as a fixed payment), any other transfer, a recurring bucket move and take-home pay. A credit card's payment follows the card and is not planned.
  - An item paid every paycheck has no history before paydays begin.
  - The steps: Income & benefits (income sources), Bills (bills other than yearly, and loan payments), Annual & save-ups (bills that come once a year or are saved up for), Spending budgets, Saving & investing (transfers and bucket moves).
  - The same suggestion is in the **too low** line of an item's By month card (`GET /api/items/{id}/plan-suggestion`).

### 5.9 Debt & decisions planner
Inputs: extra amount per month, comparison period, and the user's options. Rates for debts come from the accounts; **growth rates for investments are editable inputs** (prefilled from the account's assumed rate).
- **Pay down a debt:** amortize with the extra payment; report interest saved, new payoff date.
- **Invest:** future value of monthly contributions at the assumed rate; for a 401(k), include employer match on the portion under the match cap.
- **Payoff order:** highest rate first or smallest balance first; when a debt is paid off, its payment rolls into the next.
- Flags shown first: unclaimed employer match, promos ending.
- Always labeled as estimates for comparison, not advice.
- As built (Phase 11, `engine/planner`; decided with Rachel, 2026-10-13):
  - **What is compared**: every loan, every card carrying a balance, every investment account and every savings account (at its APY) that is not archived. Checking is not offered. Any of them can be left out (`planner_hidden_accounts`, migration `V24`) and brought back; Undo covers both. Nothing else is saved: the amount, the period and the order are remembered on the device, like Hide amounts.
  - **Comparison only**: nothing on the screen adds a payment or changes the budget. Each card's name opens its account.
  - **No tax or access claims**: the mockup's "Not until 59½", "Gains are taxed when you sell" and "Pre-tax" lines are left out. A card says only what Budget works out.
  - **Interest compounds monthly on both sides.** A debt's unpaid interest joins its balance and is charged interest from then on; an investment's growth is grown on in later months. A debt's month is rate ÷ 12 (how loans and cards charge it), an investment's is the twelfth root of the yearly rate (so 7% a year comes to exactly 7%).
  - **A debt** is followed a month at a time, the way its loan page does it (`PayoffPlan`): a month's interest (rate ÷ 12) is added, then the payment comes off. A loan uses today's balance and rate and its payment less escrow, from its next payment day, so its "was" date is the payoff date on its own page. A loan with no monthly payment entered says so and is not followed.
  - **A card** is followed at what next month's payments into it come to, held level; with none set up, at its estimated minimum. A promotional rate that covers the whole balance is used until its last day, then the rate after it; a promotion on only part of the balance leaves the card compared at its regular APR. A card paid in full every month (its own payment pays the statement or the full balance) is not offered: there is nothing to pay down. A promotional balance whose payoff is already among the recurring payments takes none of the extra and shows on the timeline as gone when the promotion ends.
  - **Extra on one debt** is that debt alone with the extra added: interest saved over its life, the new payoff date, and what is free each month afterwards (its payment and the extra). When the payment never gets ahead of the interest there is no "interest saved" to give, and the card says so.
  - **Payoff order** (`PayoffPlan.withExtra`): the extra goes to one debt at a time, highest rate or smallest balance first, chosen again each month (so a promotion ending changes the order); a debt that is gone passes its payment on from the next month. "Without" is each debt on its own payment with nothing passed on.
  - **Investing or saving** (`ContributionGrowth`): the extra put in at the end of each month, growing at the twelfth root of the yearly rate, for the period chosen (1, 3, 5, 10, 20 or 30 years). The figure is what the extra itself comes to, not the whole account. The rate is the account's assumed growth or APY and can be typed over on the card for that visit; it is never saved to the account.
  - **Employer match on the extra** (`MatchOnExtra`): for an account a formula match is paid into, the month's extra is shared over the year's paychecks and only the part still under the cap is matched. A fixed match, or one with no gross pay to check the cap against, adds nothing.
  - **Flags**, shown first: a match not earned in full (how much more a month would still be matched, and what it brings), and every promotional rate with a balance on it (when it ends, what is on it, whether its payoff is planned).

### 5.10 Overrides and edits
- Inline edit asks **Just this one** (default) or **This and all future**.
- The value at first edit is saved as `projected_amount`.

## 6. UX rules (apply to all screens)

- **Pay period screen fits one screen with no scrolling** at 1440×900; must also fit 1366×768 and 1280×800 using a compact density. Panels scroll internally only as a last resort.
- Amounts: right-aligned, tabular digits, same box width whether estimate or not. Negatives use a minus sign.
- Status is never color alone (labels/icons too). Text contrast ≥ 4.5:1. Real buttons and inputs, keyboard reachable, visible focus.
- Inline editing: click an amount to edit; Tab to next; Enter saves; Esc cancels.
- **Anything that can be opened and edited shows a visible Edit button** (decided 2026-10-08): the word "Edit" where there is room, a pencil with a tooltip in tight rows. A clickable name or row is never the only way in. A row with an Edit button can also be clicked anywhere to open it (decided 2026-10-09; `components/rowEdit`), except on something in it with its own job, such as an amount or a checkbox.
- **Dialogs and slide-outs close on a click outside them** (decided 2026-10-08), as well as on Escape and the X. If anything in them was changed and not saved, all three ask first ("Keep editing" / "Close without saving"); the form's own Cancel button discards without asking.
- **Forms are easy to tell apart and to read** (decided 2026-10-09): every dialog has a tinted header strip with an icon for what it adds or changes, in the color of the account, bucket or label being edited (the title stays in the normal text color on a light tint, so contrast holds for any color). A long form is split into titled groups on faint panels (`FormSection`), puts its amount first and large, shows icons on its type switch. ## 7. Security, backups, recovery

- **Session gate (built in Phase 0).** Every `/api` route except `GET /api/health`, `POST /api/session` and `POST /api/shutdown` requires a live session: an opaque random token in an HttpOnly, SameSite=Strict cookie, held in memory only and expiring after the auto-lock idle time. Until the PIN exists, `POST /api/session` issues a session without credentials **to requests from this PC only**; Phase 6 puts the PIN in front of it. `POST /api/shutdown` is loopback-only and needs the per-launch token the desktop shell generated.
- Requests whose `Host` header is a domain name the app was not told about are refused (DNS-rebinding protection); a strict Content-Security-Policy is sent on every response.
- **PIN** (4–8 digits) is an app lock, not encryption. Argon2 hash.
- **Recovery code** shown once at PIN setup; can reset the PIN.
- Increasing delays after wrong PINs.
- If both are lost: running the backend launcher with `--reset-pin` on the PC clears the PIN without touching data, then exits. Not available over HTTP.
- Remote sessions always require the PIN and expire with auto-lock.
- **As built (Phase 6):** the PIN is optional (decided 2026-10-11). Without one, `POST /api/session` still opens a session for this PC only, and nothing locks. `GET /api/session` is open and says whether the app is unlocked, whether a PIN is set, how long to wait after wrong tries, and whether to offer a PIN. Setting or changing it is `PUT /api/pin`, removing it `DELETE /api/pin`, both asking for the current PIN; `POST /api/pin/recovery` (open) takes the recovery code and a new PIN, and answers with a new code; `POST /api/pin/recovery-code` makes a new code. Wrong PINs and wrong codes share one count: two free tries, then waits of 30 s, 1 min, 5 min, 15 min and 1 hour, kept in the database so a restart does not clear them. The idle limit is the `auto_lock_minutes` setting, read on every request, and the screen locks itself at the same limit.
- **Backups:** daily copy (SQLite backup API) plus the `files/` folder to a user-chosen folder; keep the last N. "Back up now" and "Restore…". As built (Phase 6): one zip per backup, taken once a day while the app is open (checked half a minute after start and then hourly); the folder is chosen in an in-app browser of this PC's drives and folders (`GET`, `POST /api/folders`); restoring, choosing the folder and browsing folders work from this PC only. A restore keeps the current PIN and backup folder and first saves what is there now. The zips are not encrypted.
- **Erase all data** (Settings; built in Phase 0): permanently removes everything and leaves a fresh app, as if newly installed. The database files are deleted outright and rebuilt from the migrations (so nothing lingers in free pages or the write-ahead log), and the `files/` and in-app `backups/` folders are deleted. Logs stay; backups the user saved to another folder are not touched. It asks for confirmation with "Keep my data" as the focused default, cannot be undone (Undo does not cover it), ends every session, and from Phase 6 also removes the PIN. `DELETE /api/data` requires a session, an explicit confirmation phrase in the body, and a request from this PC — it is never available from the phone.
- **Attached files (Phase 7):** served only by attachment id behind the session, never by path or name; downloads carry `Content-Disposition: attachment` and `nosniff`, and a PDF is previewed as a picture the backend draws, so nothing inside an uploaded file is ever run by the window. File names and payees are not logged. Exports guard spreadsheet cells against formulas.
- Docs recommend Windows BitLocker for at-rest protection.

### Dependencies and the build pipeline
- **CI** (`.github/workflows/ci.yml`, GitHub Actions) runs on every push to a branch: backend tests (on Windows, where the app ships), frontend typecheck/tests/build, and the dependency checks below. **Nothing runs on a push to `main`**: work only reaches main through a pull request whose branch already passed them. **The installer is built in CI only when asked for by hand** ("Run workflow"; Rachel, 2026-10-13): an hour on a Windows runner is billed double, and building it on every merge, then on every branch push, used most of a month's allowance. The installer to try is built on the PC with `build-installer.ps1`, which tests before packaging. The manual CI job waits for the two test jobs, then runs `build-installer.ps1 -SkipTests` (the suites have just run on that commit) and keeps the result as a workflow artifact. The installer job keeps between runs the Tauri command-line tool (one fixed version), Cargo's package downloads (checksummed by `Cargo.lock`) and the **compiled dependencies** (`desktop/src-tauri/target`, keyed on the compiler version, the Tauri tool version and `Cargo.lock`); the shell's own crate and the bundle folder are deleted first, so the app itself is always compiled from clean. Actions are pinned to commit hashes; the workflow token is read-only and needs no secrets. This is build-time only — the app itself still makes no outbound calls.
- **Known vulnerabilities:** OSV-Scanner checks every Maven (direct and transitive, from a CycloneDX list), npm and Cargo dependency on every branch push and weekly, and fails the build on a finding. A real, known vulnerability never passes. `desktop/src-tauri/osv-scanner.toml` lists, with reasons, the only findings the scan passes over: two Linux-only crates that are not in the Windows build. (The five `unic-*` notices passed over until 2026-10-15 are gone: Tauri 2.12.0 turned 14 days old and was taken in Phase 8, and it no longer uses those crates.)
- **No dependency younger than 14 days.** A release that new has not been out long enough for a vulnerable or hijacked version to be noticed. `check-dependency-age.ps1` enforces it in CI for versions a branch adds or changes, and `min-release-age=14` in `frontend/.npmrc` at install time. The same applies to pinned Actions.
- **When the two rules collide** (the only fix for a vulnerability is younger than 14 days), in this order: (1) use an older version that never had the vulnerability; (2) drop or replace the package, if nothing the app needs is lost; (3) only then take the fixed version early, as a named entry in `dependency-age-exceptions.json` saying what it fixes and why 1 and 2 were not possible. An exception ends by itself: the check looks every entry up on every run (weekly included) and fails once the version is 14 days old, or no longer used, until the entry is deleted. Current exceptions: none (the `source-map-js` 1.2.2 entry was removed in Phase 11, the day before it turned 14 days old).

How it works, where the spec left it open:

- A report covers whatever falls in its dates. Days still to come and amounts marked as estimates are counted, shaded light blue, and totalled separately as "Estimated or still to come".
- Bills and budgets in a report come from recurring items that are not archived, the same as the pay period screens. Reimbursement applies to one-off spending only.
- There is no "all time" range: Custom dates reach ten years.
- A saved report whose tag, category or account has since been deleted opens without that filter and says it has changed.
- A PDF holds at most 300 receipts; a report with more says so and asks for narrower dates. A receipt that cannot be read is listed on a last page, "Files that could not be added", and the rest still export.
- The PDF is set in Segoe UI or Arial from the PC's own fonts folder (nothing is bundled or downloaded), falling back to the built-in Helvetica.
- A document dragged straight out of a web page arrives as a link, not a file. Budget makes no outbound calls, so it does not fetch it: the receipt box says to download it first and drop it from the browser's downloads list or its folder (Rachel, 2026-10-12).
- The desktop window no longer handles dropped files itself, so a drop reaches the page.
- **Saving a file** (Rachel, 2026-10-12: "export pdf doesn't seem to do anything"). The desktop window saves a file handed to it without showing anything, and refuses the ones after the first. So an export, or "Save a copy" of a receipt, asked for from this PC is written by the backend into the Downloads folder (`BUDGET_DOWNLOADS_DIR`, else `%USERPROFILE%\Downloads`), never replacing a file ("Report (2).pdf"), and the screen says "Saved in … as …". Asked from anywhere else (the phone, Phase 12) the file is sent back for that browser to save. Saving a file is not a change to the budget, so Undo does not cover it.
- In the PDF a line not paid yet says "Not paid yet" in a Status column and is not shaded; the light blue box is only for an amount that is itself an estimate (Rachel, 2026-10-12). The CSV has a "Not paid yet" column.
- The report's figures are one card in one row from a tablet up, two across on a phone, like the figures at the top of Expenses.
- **Save** for a report sits under the choices it saves; folded away, it shows only when the report differs from what was saved. **Clear the form**, there once something has been chosen on a new report, asks before it clears. "New report" is a choice in the Report picker.
- An expense's page has **See its pay period**, which opens the pay period its date falls in; it is not shown when no pay period holds that date.
- A recurring **bill** is called "Bill or expense" wherever the kind is named (regular spending nobody bills you for works the same way); "More options" on its form shows only when there is a bucket to save up in.

**Pop-up forms measured** at 1366×768 and 375×812 in headless Edge, with room left for an error message; none scrolls:

- **The one-off form** (money out, money in, transfer) was the last long form left, and the new fields made it longer. It now goes a screen at a time like the others. Adding: the amount and what it is, then when and which account, and **Add** is there; **More options** leads to who it was paid to, category, tags and note, then the receipt and paying back, then setting aside in buckets (two buckets at a time). The switch between money out, money in, transfer and recurring is on the first screen only. Changing: one group at a time under "What to change" (Amount, When and where, Details, then the bucket, pays back and set aside where they apply, and Delete). The groups follow the cards of the expense's page: the Details card's pencil opens the form on Details, which holds what that card shows (category, tags, note, check number), and "Edit expense" at the top opens it on Amount (Rachel, 2026-10-12).
- **Receipts in a dialog** (a pay period row, a card statement) show one file at a time with "File 2 of 5", so twenty files take no more room than one. An expense's own page lists them all.

Not in this phase: a paperclip on pay period rows that have a receipt (the count is shown in the row's form); WebP and HEIC pictures (§4.8); receipts on pay stubs (a stub keeps its own PDF, Phase 8); adding a receipt from the phone's camera (Phase 12).
